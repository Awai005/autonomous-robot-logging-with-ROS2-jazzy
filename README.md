# Robot Navigation with Blockchain Logging

## Overview
This package integrates a ROS2 Jazzy node with a local Ethereum blockchain (using Ganache) to log robot navigation data as transactions. Each time the robot reaches a navigation goal, it saves a transaction containing a timestamp, position, and status message to the blockchain.

## Prerequisites
- **Ubuntu 24.04** with **ROS2 Jazzy** installed.
- **Python 3.12** (default with Ubuntu 24.04).
- **Node.js and npm** for Ganache installation.
- **Python `web3` library**: Install with `pip install web3`.
- A working ROS2 navigation stack (e.g., Nav2) with Gazebo Harmonic.

## Main ROS2 Functionality

This section describes the core ROS2 functionality for the autonomous robot navigation and logging experiment. The system integrates a simulated mobile robot in Gazebo Harmonic, equipped with a LiDAR sensor, to perform mapping, navigation, and waypoint following, with data logged to a blockchain. Below, we outline the key components: LiDAR sensor selection and integration, manual teleoperation and mapping, Nav2 setup, controller compatibility, and the waypoint runner node with blockchain integration.

### LiDAR Sensor Selection and Gazebo Plugin
To enable environment perception, a 2D LiDAR sensor was chosen for its balance of range, resolution, and compatibility with ROS2’s navigation stack. The Hokuyo UST-10LX LiDAR was selected due to its 10-meter range, 270-degree field of view, and high accuracy, suitable for indoor mapping and navigation. The sensor is integrated into the Gazebo simulation by adding a plugin to the world file (`world.sdf`) or the robot’s URDF/SDF model.

The Gazebo plugin for the LiDAR is defined as follows:
- **Plugin**: `libgazebo_ros_ray_sensor.so` (from `gazebo_ros_pkgs`).
- **Topic**: Publishes laser scans to `/scan`.
- **Configuration**: Configured with a 270-degree field of view, 1080 samples per scan, and a 10-meter range to match the UST-10LX specifications.

Example snippet in the robot’s SDF:
```xml
<sensor name="lidar" type="ray">
  <pose>0 0 0.1 0 0 0</pose>
  <ray>
    <scan>
      <horizontal>
        <samples>1080</samples>
        <resolution>1</resolution>
        <min_angle>-2.35619</min_angle>
        <max_angle>2.35619</max_angle>
      </horizontal>
    </scan>
    <range>
      <min>0.1</min>
      <max>10.0</max>
    </range>
  </ray>
  <plugin name="lidar_plugin" filename="libgazebo_ros_ray_sensor.so">
    <ros>
      <remapping>~/out:=scan</remapping>
    </ros>
    <update_rate>40</update_rate>
  </plugin>
</sensor>
```

The world file is launched with Gazebo:
```bash
ros2 launch gazebo_ros gazebo.launch.py world:=<path_to_world.sdf>
```
This setup ensures the robot can perceive its environment, providing scan data for mapping and navigation.

### Manual Teleoperation and Mapping
To create a map of the environment, the robot is manually driven using the `teleop_twist_keyboard` package, and the `slam_toolbox` package is used for Simultaneous Localization and Mapping (SLAM).

- **Teleoperation**:
  The `teleop_twist_keyboard` package publishes `geometry_msgs/Twist` messages to the `/cmd_vel` topic, allowing manual control of the differential drive robot:
  ```bash
  ros2 run teleop_twist_keyboard teleop_twist_keyboard
  ```
  The robot is driven through the environment to collect LiDAR data, ensuring coverage of all areas for a complete map.

- **SLAM with `slam_toolbox`**:
  The `slam_toolbox` package processes `/scan` data to generate a 2D occupancy grid map. A custom launch file, `mapping.launch.py`, is used to start the SLAM pipeline:
  ```python
  from launch import LaunchDescription
  from launch_ros.actions import Node

  def generate_launch_description():
      return LaunchDescription([
          Node(
              package='slam_toolbox',
              executable='async_slam_toolbox_node',
              name='slam_toolbox',
              output='screen',
              parameters=[{
                  'use_sim_time': True,
                  'slam_toolbox.odom_frame': 'odom',
                  'slam_toolbox.map_frame': 'map',
                  'slam_toolbox.base_frame': 'base_link',
                  'slam_toolbox.transform_publish_period': 0.02,
              }],
              remappings=[('/scan', '/scan')]
          )
      ])
  ```
  Launch the mapping process:
  ```bash
  ros2 launch waypoint_runner mapping.launch.py
  ```
  During teleoperation, `slam_toolbox` builds the map, which is saved using:
  ```bash
  ros2 run nav2_map_server map_saver_cli -f my_map
  ```
  This generates `my_map.pgm` and `my_map.yaml` in the current directory, used later for navigation.

### Nav2 Setup with Generated Map
The Navigation2 (Nav2) stack is configured to enable autonomous navigation using the map generated by `slam_toolbox`. The Nav2 stack includes components for localization, planning, and control.

- **Launch Nav2**:
  A custom launch file, `navigation_launch.py`, starts the Nav2 stack with the saved map:
  ```python
  from launch import LaunchDescription
  from launch_ros.actions import Node
  from ament_index_python.packages import get_package_share_directory
  import os

  def generate_launch_description():
      nav2_params = os.path.join(
          get_package_share_directory('waypoint_runner'),
          'config', 'nav2_params.yaml'
      )
      map_file = os.path.join(
          get_package_share_directory('waypoint_runner'),
          'maps', 'my_map.yaml'
      )
      return LaunchDescription([
          Node(
              package='nav2_map_server',
              executable='map_server',
              name='map_server',
              output='screen',
              parameters=[{'yaml_filename': map_file, 'use_sim_time': True}]
          ),
          Node(
              package='nav2_amcl',
              executable='amcl',
              name='amcl',
              output='screen',
              parameters=[nav2_params]
          ),
          Node(
              package='nav2_controller',
              executable='controller_server',
              name='controller_server',
              output='screen',
              parameters=[nav2_params]
          ),
          Node(
              package='nav2_planner',
              executable='planner_server',
              name='planner_server',
              output='screen',
              parameters=[nav2_params]
          ),
          Node(
              package='nav2_recoveries',
              executable='recoveries_server',
              name='recoveries_server',
              output='screen',
              parameters=[nav2_params]
          ),
          Node(
              package='nav2_bt_navigator',
              executable='bt_navigator',
              name='bt_navigator',
              output='screen',
              parameters=[nav2_params]
          ),
          Node(
              package='nav2_lifecycle_manager',
              executable='lifecycle_manager',
              name='lifecycle_manager_navigation',
              output='screen',
              parameters=[{'use_sim_time': True, 'autostart': True, 'node_names': [
                  'map_server', 'amcl', 'controller_server', 'planner_server',
                  'recoveries_server', 'bt_navigator']}]
          )
      ])
  ```
  Create a `nav2_params.yaml` file in `waypoint_runner/config/` with parameters for AMCL, controller, and planner (e.g., DWB controller for differential drive). Launch Nav2:
  ```bash
  ros2 launch waypoint_runner navigation_launch.py
  ```

- **Map and Localization**:
  The map server loads `my_map.yaml`, and AMCL (Adaptive Monte Carlo Localization) localizes the robot using `/scan` and `/odom` data. The Nav2 controller and planner compute paths to goals via the `/navigate_to_pose` action.

### Controller Compatibility with `ros2_control`
To ensure compatibility between Nav2 and the robot’s differential drive, the `ros2_control` framework is used with a differential drive controller. The robot’s URDF includes a `diff_drive_controller` plugin, publishing `/cmd_vel` and subscribing to `/odom`.

- **Twist Compatibility**:
  The `waypoint_runner` node sends `NavigateToPose` goals, which Nav2 converts to `geometry_msgs/Twist` commands compatible with the `diff_drive_controller`. The controller configuration in `nav2_params.yaml` ensures proper scaling:
  ```yaml
  controller_server:
    ros__parameters:
      use_sim_time: true
      controller_plugins: ["FollowPath"]
      FollowPath:
        plugin: "dwb_core::DWBLocalPlanner"
        max_vel_x: 0.5
        max_vel_theta: 1.0
        min_vel_x: 0.0
        min_vel_theta: 0.0
  ```
  A twist compatibility node (e.g., `twist_ensurer.py`) monitors `/cmd_vel` to ensure commands are within limits:
  ```python
  import rclpy
  from rclpy.node import Node
  from geometry_msgs.msg import Twist

  class TwistEnsurer(Node):
      def __init__(self):
          super().__init__('twist_ensurer')
          self.sub = self.create_subscription(Twist, '/cmd_vel', self.callback, 10)
          self.pub = self.create_publisher(Twist, '/cmd_vel_ensured', 10)
          self.max_linear = 0.5
          self.max_angular = 1.0

      def callback(self, msg):
          twist = Twist()
          twist.linear.x = max(min(msg.linear.x, self.max_linear), -self.max_linear)
          twist.angular.z = max(min(msg.angular.z, self.max_angular), -self.max_angular)
          self.pub.publish(twist)

  def main():
      rclpy.init()
      node = TwistEnsurer()
      rclpy.spin(node)
      node.destroy_node()
      rclpy.shutdown()

  if __name__ == '__main__':
      main()
  ```
  Update `setup.cfg` to include:
  ```ini
  console_scripts =
      visit_points = waypoint_runner.visit_points:main
      twist_ensurer = waypoint_runner.twist_ensurer:main
  ```
  Run:
  ```bash
  ros2 run waypoint_runner twist_ensurer
  ```

### Waypoint Runner Node with Blockchain Logging
The `waypoint_runner` node (`visit_points.py`) orchestrates autonomous navigation to predefined waypoints and logs data to a blockchain using `web3.py` and Ganache.

- **Waypoint Navigation**:
  The node defines four waypoints: `(-6.25, 0.0, 0.0)`, `(0.0, 3.25, 1.57)`, `(6.25, 0.0, 3.14)`, and `(0.0, 0.0, 0.0)`. It uses the `NavigateToPose` action to send goals to Nav2:
  - Converts yaw to quaternion using `yaw_to_quat`.
  - Sends goals via `/navigate_to_pose` and waits for completion.
  - Logs status with `rclpy` logging.

- **Blockchain Integration**:
  Upon reaching each waypoint, the node logs:
  - Timestamp (Unix time).
  - Position (x, y, z).
  - Status message (e.g., “Reached waypoint 1”).
  Data is sent as a transaction payload to a local Ganache blockchain (`http://127.0.0.1:8545`):
  ```python
  self.web3 = Web3(Web3.HTTPProvider('http://127.0.0.1:8545'))
  data_str = f"Timestamp: {int(time.time())}, Position: x:{x:.2f} y:{y:.2f} z:0.00, Message: Reached waypoint {i}"
  txn = {'to': self.account, 'value': 0, 'gas': 2000000, 'gasPrice': self.web3.to_wei('1', 'gwei'), 'nonce': self.web3.eth.get_transaction_count(self.account), 'data': data_str.encode()}
  tx_hash = self.web3.eth.send_transaction(txn)
  ```
  Transactions are retrieved and logged for verification.

- **Execution**:
  ```bash
  ros2 run waypoint_runner visit_points
  ```

## Blockchain Setup with Ganache
The node uses Ganache to simulate a local Ethereum blockchain for logging transactions.


### Running Ganache
- **CLI**: Start Ganache to run a local blockchain on `http://127.0.0.1:8545`:
  ```bash
  ganache
  ```
  Note the first account address (e.g., `0x...`) displayed in the terminal.


### Building the Package
```bash
cd ~/ros2_ws
colcon build --packages-select my_robot_nav
source install/setup.bash
```

### Running the Node
1. Start Ganache (CLI or GUI) to ensure the blockchain is running.
2. Launch your ROS2 navigation stack and Gazebo simulation:
   ```bash
   ros2 launch <your_nav_package> <your_nav_launch_file>
   ```
3. Run the node:
   ```bash
   ros2 run waypoint_runner visit_points
   ```
   The node sends a test goal to `/navigate_to_pose` and logs a transaction when the goal is reached. To use with actual navigation goals, modify the node to subscribe to `/goal_pose` or integrate with your navigation pipeline.

### Transaction Logging
- When the robot reaches a goal, the node sends a transaction with:
  - **Timestamp**: Unix epoch time (e.g., `1739876543`).
  - **Position**: Robot’s coordinates (e.g., `x:1.00 y:2.00 z:0.00`).
  - **Message**: Status (e.g., `Reached waypoint_2`).
- The transaction hash and decoded data are logged to the console:
  ```
  [INFO] [nav_goal_logger]: Transaction hash: 0x123...
  [INFO] [nav_goal_logger]: Transaction 0x123... details:
  [INFO] [nav_goal_logger]:   Data: Timestamp: 1739876543, Position: x:1.00 y:2.00 z:0.00, Message: Reached waypoint_2
  ```

## Troubleshooting
- **Ganache Connection**: Ensure Ganache is running and the port matches (`8545` for CLI, `7545` for GUI).
- **web3 Errors**: Verify `web3` is installed (`pip show web3`) and matches your Python version.
- **Navigation Issues**: Ensure `/navigate_to_pose` action server is active (`ros2 action list`).
- **Build Errors**: Check `colcon build` logs and verify `package.xml`/`CMakeLists.txt` dependencies.
